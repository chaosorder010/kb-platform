# 代码约定

dotdot 代码约定，用于保持实现简单且易于维护。

## 抽象边界

- 不要引入不必要的抽象。
- 不要抽象没有复用场景的代码。
- 如果复用行为未来可能拆分为不同功能或流程，不要因为当前已经复用就立即抽象。
- 在稳定的复用模式出现前，优先使用局部且显式的代码。

## 源文件大小

- 源文件应保持足够小，使人类和编码 agent 能在一次专注阅读中理解。
- 代码超过 150 行时，即使尚未复用，也应考虑拆分或提取职责聚焦的模块。
- 接近 250 行时，应按职责检查是否需要提取。
- 按行为或职责拆分，不要按任意的技术层级拆分。

## dotdotgod 影响热点

- 如果多次执行 `dotdotgod graph impact` 的结果都集中到同一个大文件上，应将其视为设计信号，而不是正常的精度表现。
- dotdotgod 影响分析可以揭示混合职责热点，但不能替代聚焦的模块边界。
- 如果无关变更持续指向同一个源文件，应按行为拆分该文件，让影响分析、测试和文档能够映射到更窄的职责范围。

## 提取与可测试性

- 当行为可以脱离运行时依赖测试时，优先提取纯函数或纯逻辑。
- 在复用稳定前，让运行时集成保持显式且局部。
- 在添加宽泛的框架抽象前，先将可测试逻辑放入职责聚焦的模块。
- 保持纯文本可读性：避免密集的巧技、隐藏控制流和大型混合职责文件。
